# storybook/ layout and file formats

Everything the skill creates lives here; all files below except the shell are language-neutral.

```text
storybook/
  kit/                  # vendored kit: sbk checker (Rust dev tool) + viewer sources + per-language templates
  views.toml            # authored: census of views
  inventory.json        # generated by `sbk scan` (do not edit): extractors, views, axes, actions, findings
  states/<view>.toml    # authored: classes, guards, equivalences, dispositions
  fixtures/<view>/<state>.json   # generated then curated: one canonical VM per cell
  fixtures/captured/    # optional: NDJSON from the capture probe (curate into cells)
  flows.toml            # authored: roots + edges + data variants
  layout.json           # generated by `sbk verify`: deterministic journey coordinates (flow nodes, variants, merged edges)
  validate…             # host-language fixture validator (from the adapter)
  <shell>               # host-language storybook app (from the adapter templates)
```

  Curated fixtures may use any declared variant of an enum (in a field,
  option, collection or map); the chosen variant's payload must match the
  skeleton, and an unknown variant name is drift. A collection's size
  class applies only when the collection is an axis of the view; any
  other collection or map may have any length (elements still checked).
  A field with `#[serde(default)]` may be omitted from a curated fixture
  or present with any value matching its skeleton; generated fixtures
  include the key.

## views.toml
```toml
lang = "python"                    # rust | python | c | vala | gjs
[[view]]
id = "skill_detail"
entry = "app/pages/skill_detail.py:build"     # or a template class + set_vm method
vm = "app.models.SkillDetailVm"
actions = "app.pages.skill_detail.SkillDetailActions"   # or "signals" / "action-group"
template = "app/ui/skill_detail.ui"            # optional .ui / .blp
```

## states/<view>.toml
```toml
view = "skill_detail"
title = "Szczegóły skilla"           # optional display name (sidebar,
                                     # cluster and lane labels); without
                                     # it the id is humanized
budget = 64

[classes]
"name" = ["short", "overflow"]
"rows" = ["empty", "one", "many"]
"filter" = ["none", "broken", "conflict"]      # GFlags: combinations the view distinguishes

[[guard]]
when = { "phase" = "pending", "rows" = "many" }
reason = "rows load only after the phase completes"   # evidence: file:line

[[equivalence]]
axis = "description"
merge = ["short", "any"]
reason = "single-line ellipsized label"

[disposition]
"f-3c9a1e" = { covered-by = "skill_detail/dirty" }
"f-77b012" = { excluded = "scroll position is not presentation state" }

[titles]
# state id -> human title; the viewer labels nodes with it (falls back to
# the state id) and `sbk check titles` gates coverage (verify is strict).
"skill_detail/dirty-empty" = "Edycja niezapisanych zmian"

[labels]
# optional story-menu names: "<axis>" names a data dimension,
# "<axis>.<class>" one of its final classes (fallback: humanized ids);
# `sbk expand` reports a key naming no axis or class as a problem
"scopes" = "Zasięg"
"scopes.many" = "globalny + projekt"
```
State ids: `<view>/<class>-<class>-…` in axis order (from `sbk expand`); a story may add a human `title` in `[titles]` — nodes *and* data variants (the sidebar rows and the expanded variant grid show it).

## flows.toml
```toml
roots = ["onboarding/agents-ready"]          # several when startup is conditional

[[edge]]
from = "shell/normal"
action = "on_new_skill"                       # action port name (callback, signal or GAction)
to = "create/empty"
label = "New skill"

[[edge]]
from = "create/valid"
action = "on_cancel"
to = "back"                                   # pop the navigation history of the path

[[terminal]]
state = "skill_detail/plain"
action = "on_copy_path"
kind = "self"                                 # self = stays in place; leaf = intended end

[variants]
"skills/many" = ["skills/empty", "skills/one", "skills/long-names"]
```

### Flow nodes and data variants

A **flow node** is a state that appears in `roots`, in any edge (from, or
to ≠ `back`) or as a terminal state: a user-reachable step of the journey.
Every other cell **must** be a **data variant** of exactly one flow node —
listed in `[variants]`. `sbk check flows` enforces:

* every cell in `cells.json` is either a flow node or a variant of exactly
  one flow node (a state in two places, or in neither, is red);
* a variant never appears in `roots`, edges or terminals — edges connect
  flow nodes only;
* a variant belongs to the same view as its flow node;
* every (flow node, action) pair has an edge or a terminal; variants share
  their node's wiring;
* every flow node is reachable from a root (variants are covered via
  their node).

`layout.json` gives only flow nodes journey columns (longest path from the
roots over the DAG obtained by dropping back edges); variants are listed
separately with `variant_of` and a stack position under their node.

The `engine` field says who placed the geometry: `"dot"` (Graphviz, see
below) or `"builtin"`. Both carry the same nodes/variants/edges with
lane/depth/order, titles, self actions and variant counts, so the checker
and older consumers keep working.

## layout.json engines

`sbk verify` prefers Graphviz `dot` when it is on `PATH`; `SBK_DOT=/path`
overrides the binary, `SBK_DOT=off` forces the builtin engine. Graphviz is
an optional dependency of the storybook (recommended: better edge routing
and per-view clusters). When dot is missing or fails, verify still goes
green on the builtin engine and prints a warning line.

A `"dot"` layout adds, on top of the builtin fields (all px, y grows down,
top-left based):

- `dot_version` — the Graphviz version string;
- per node `rect` (`x`, `y`, `w`, `h`) — where the viewer draws the node;
- per edge `points` — the spline as a cubic Bezier chain (start point,
  then whole triples c1/c2/end; one `cubic_to` per triple), `label_pos` —
  the label pill centre, and `arrow` — the filled arrowhead polygon;
- `clusters` — one per view: `view`, `label` (the view display name from
  `view_titles`, else the view id, shown on top of the frame) and `rect`.

Both engines also write:

- `view_titles` — view id -> authored display name
  (`states/<view>.toml` top-level `title`); consumers fall back to
  humanizing the view id (`skill_detail` → "Skill detail");
- per variant `title` — the variant's `[titles]` entry, else `None`
  (consumers fall back to the classes part of the state id).

The same input yields a byte-identical file in either engine. The viewer
draws dot layouts from the stored geometry (nodes at their rects, edges as
the stored chains, cluster frames with the view display name); the builtin
engine draws exactly as before.
